# 任务卡模板

OpenClaw 接到复杂任务后，先在内部填好这张卡。卡片不对用户展示，但卡片内容决定后续所有动作。

## 字段定义

| 字段 | 必填 | 说明 |
|------|------|------|
| 任务名称 | ✅ | 一句话描述要做什么 |
| 任务类型 | ✅ | 写作 / 整理 / 分析 / 规划 / 执行辅助 / 混合 |
| 最终交付物 | ✅ | 结果长什么样（格式、篇幅、可直接用的形式） |
| 输入材料 | ✅ | 可用的文件、目录、对话片段；若无则写"无" |
| 关键约束 | ✅ | 输出格式、风格、时间、禁止项、确认节点 |
| 风险点 | ✅ | 哪里容易跑偏、越界、误判 |
| 最小闭环动作 | ✅ | 第一个最小、最安全、最能验证方向的动作 |
| 是否需要 Hermes | ✅ | 是 / 否；写明理由 |
| 是否需要人工确认 | ✅ | 是 / 否；哪些节点必须停下来 |
| 验收标准 | ✅ | 用户什么情况下会说"可以直接用了" |

## 示例 1 — 写作类

```yaml
任务名称: 给张总写项目周会邮件
任务类型: 写作类
最终交付物: 一封 200 字内、语气正式、可直接发送的邮件
输入材料:
  - ./会议纪要-2026-04-23.md
  - 用户口述的 3 个重点
关键约束:
  - 不超过 3 段
  - 语气正式但不生硬
  - 不能泄露未确认的数字
风险点:
  - 误把草案数据当作最终数据写入邮件
  - 被纪要里无关议题带偏
最小闭环动作: 先从纪要提炼 3 个要点并回读给用户确认
是否需要 Hermes: 是  # 理由: 需要读取纪要并提炼
是否需要人工确认:
  节点:
    - 要点提炼完成后
    - 邮件初稿完成后
  理由: 输出将直接对外发送，后果不可逆
验收标准:
  - 用户确认 3 个要点准确
  - 用户可直接复制邮件发送
  - 格式符合公司邮件规范
```

## 示例 2 — 整理类

```yaml
任务名称: 整理 3 份产品调研资料的共同结论
任务类型: 整理类
最终交付物: 一份结构化 Markdown 文档（重点结论 + 待办清单）
输入材料:
  - ./research-A.md
  - ./research-B.md
  - ./research-C.md
关键约束:
  - 不抄原文，要归纳
  - 必须区分共识与分歧
  - 每个结论必须有出处
风险点:
  - 把单一资料的观点当成共识
  - 遗漏反对意见
最小闭环动作: 先读一份资料，输出样例结构，让用户确认再批量处理
是否需要 Hermes: 是  # 理由: 需要分析 3 个文件
是否需要人工确认:
  节点:
    - 样例结构完成后
  理由: 结构错了后面全白做
验收标准:
  - 每条结论标注来源
  - 共识与分歧分开列
  - 有明确的后续行动项
```

## 多图成品任务附加字段（新增）

当任务目标是“最终图片/多图成品交付”时，在基础模板上额外补充以下字段：

```yaml
成品类型: 连贯漫画 / 系列海报 / 多视角效果图
输出目录:
探针图要求: 先只生成第1张并验证真实落盘
批量策略: 逐张生成 / 逐张超时 / 逐张记录
交付分级:
  - 正式版：全部图片落盘
  - 预览版：部分图片落盘
  - 方案版：仅文本方案与提示词
失败后最小恢复动作:
  -
```

### 多图任务最小示例

```yaml
任务名称: 生成 6 张通勤飞书漫画
任务类型: 混合（规划 + 成图交付）
最终交付物: 6 张实际图片文件 + 对应 prompt + 落盘结果清单
输入材料:
  - 主题描述
关键约束:
  - 角色一致
  - 画风一致
  - 不得复刻真实 logo
风险点:
  - 图片后端超时
  - 整批渲染导致 0 图落盘
最小闭环动作: 先生成第1张探针图并验证落盘
是否需要 Hermes: 是  # 理由: 需要做设定、分镜、提示词和图片生成
是否需要人工确认:
  节点:
    - 探针图生成后
  理由:
    - 首图风格决定后续 5 张是否值得继续
验收标准:
  - 至少先验证首图真实落盘
  - 全量成功时 6/6 图片存在
```

## 使用建议

1. **任何复杂任务都先填卡**。填不出来某个字段，说明需求还没澄清，不要急着执行。
2. **字段越具体越好**。"可直接使用"比"写一份好的方案"强 10 倍。
3. **风险点写不出来，就去读材料**。靠猜写出来的风险点没用。
4. **最小闭环动作必须是一个动作，不是一个阶段**。"先读一份资料"是动作，"完成分析"不是。
