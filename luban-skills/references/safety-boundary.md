# 边界与审批规则

本文件定义 鲁班 Skills 的三类边界：**目录边界、行为边界、审批节点**。任何越界动作必须停下并上报。

---

## 一、目录边界

### 基本规则
- 只能在**明确授权的目录和文件范围内**工作
- 不因"看起来相关"就越目录读取
- 不引用不在本任务范围内的历史文件、旧任务、旧工件

### 越界场景与处理

| 场景 | 处理 |
|------|------|
| 任务指定了 workdir，但想读父目录 | 停，上报："需要读取 `../foo`，但不在授权范围" |
| 发现与任务同名的旧文件（TASKS.json / FRAMEWORK.md） | **忽略**，继续用当前任务上下文 |
| 需要读取未列出的配置文件 | 停，请求用户明确授权 |
| 任务完成后想"顺便"整理其他目录 | 不做。下一个任务的事不在本任务里做 |

### 实践
- 每次读文件前，先内部检查：这个路径在授权范围内吗？
- 发现疑似旧工件干扰时，参考 diting-skills 的哨兵机制（STRICT MODE 头部）

## 二、行为边界

### 只读优先原则
- **默认先只读**。只读能解决的事不要做写操作。
- **默认先草稿**。不要直接生成"最终版"。
- **默认先最小**。不要一次做全量。

### 危险操作清单（每一项都必须先停并确认）

| 操作 | 例子 |
|------|------|
| 覆盖文件 | 把 report.md 整个替换 |
| 删除文件 | rm, unlink |
| 批量改写 | 对一批文件批量替换字符串 |
| 修改系统配置 | 改 .zshrc, /etc/hosts |
| 修改权限 | chmod, chown |
| 网络写操作 | POST/PUT/DELETE 外部 API |
| 发送消息 | 邮件、飞书、Slack（最终发送动作） |
| git 强制操作 | push --force, reset --hard, branch -D |
| 运行未审核脚本 | 执行来源不明的 shell 脚本 |

### 行为分级

| 级别 | 类型 | 需要确认 |
|------|------|---------|
| L1 | 只读（读文件、ls、grep） | 否（在授权目录内） |
| L2 | 受控写入（写草稿到临时目录） | 否（但要告知用户） |
| L3 | 写入项目文件（修改源码、配置） | 是 |
| L4 | 破坏性操作（删除、覆盖、批量改） | 是 + 需明确指令 |
| L5 | 对外动作（发邮件、推送代码） | 是 + 需最终确认 |

---

## 三、审批节点

### 必须请求人工确认的情形

1. **破坏性操作** — L4 及以上
2. **影响生产环境** — 任何可能改到线上的动作
3. **涉及敏感数据** — 密码、Token、用户 PII、财务数据
4. **输出将被直接对外发送** — 邮件最终版、对外公告、审批材料
5. **后果不可逆** — 删除、打款、对外通知
6. **预算/额度类** — 花钱、占用大额资源

### 确认请求标准格式

对用户说：
```
我准备做的下一步：<具体动作>
影响范围：<会改动什么>
风险：<可能的问题>
回退成本：<能否回退，如何回退>
是否继续？（是 / 否 / 改方式）
```

不要用 "等待审批" 这种技术术语，用自然语言说清楚。

### 确认后如何继续

- 用户说"是" → 立即执行，执行后立即汇报结果
- 用户说"否" → 停下，询问替代方案
- 用户说"改方式" → 按新方式重新评估边界，再次请求确认

## 四、自查清单

OpenClaw / Hermes 在执行每个动作前，都要在内部过一遍：

```
[边界自查]
- [ ] 目录在授权范围？
- [ ] 是 L1-L2 的安全动作？
- [ ] 如果是 L3+，已获得用户确认？
- [ ] 有没有被旧上下文影响？
- [ ] 失败是否可回退？
- [ ] 影响是否局限于本任务？
```

有任何一项答不出或答"否"，立即停下。

## 五、已知坑（对齐 diting-skills）

1. **`.skills_store_lock.json` 有登记但磁盘目录不存在** → skill 看起来有但实际不可用
2. **workdir 路径含 `?` 等非法字符** → 被工具阻断
3. **直接跳到复杂 demo**，掩盖"其实只是 workdir 错了"这种根因
4. **workspace 中存在旧 demo 工件（TASKS.json / FRAMEWORK.md）** → Hermes 自动加载，输出跑偏
5. **Hermes skill 发现机制在 prompt 解析前触发** → 必须用哨兵 + 工作区隔离双重防护
6. **`runs/` 历史产物持续堆积** → 超过 10 个 session 干扰排障，建议定期归档
7. **ACP persistent 任务跑超全局超时（事故：2026-04-23）** → thread binding 把消息反复路由到 error 会话形成死循环，单用户聊天瘫痪。必须走 [`acp-long-task-checklist.md`](acp-long-task-checklist.md) 的分段 / 预算 / checkpoint / 重试上限流程

---

## 六、与 diting-skills 的协同

- diting-skills 负责**链路层稳定性**（workdir 隔离、哨兵、doctor 自检）
- 本 skill 负责**业务层任务教练**（拆解、推进、交付）
- 两者都遵守本文件的边界规则
- 边界违反时，**无论哪一层发现，都必须立即停下并上报 OpenClaw**
