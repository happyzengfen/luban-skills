# ACP 长任务规避清单（防超时与死循环）

> **背景**：2026-04-23 出现过一次 ACP 后台任务超时事故（issue-acp-thread-timeout-2026-04-23）。一个 GitHub 项目分析任务因网络抓取 + 多轮 LLM 推理 + 脚本执行，连续超过 600s 超时；thread binding 又把用户消息反复路由到 error 状态会话，形成死循环，单用户聊天功能完全不可用。
>
> 本文是 OpenClaw / Hermes 通过 ACP 调度长任务时的**强制规避清单**。任何"看起来可能跑超 5 分钟"的任务，必须先过一遍这份清单。

---

## 一、任务时长预估（动手前必做）

接到任务后，先在内部估算时长。**估不出来就按"长"处理。**

| 信号 | 时长档 | 处理方式 |
|------|--------|----------|
| 单文件读取 + 单轮回答 | 短（< 1 min） | 直接执行 |
| 多文件读取 + 归纳 | 中（1-5 min） | 标准 ReAct 循环 |
| 网络抓取 / 外部 API 调用 | 长（5-30 min） | **必须分段 + 进度回报** |
| 多轮 LLM 推理（≥ 3 轮） | 长 | **必须分段 + checkpoint** |
| 跨任务依赖 / 等待外部审批 | 极长（> 30 min） | **拆成多个独立子任务**，不在一个 ACP 会话里跑完 |

**判定问句（OpenClaw 内部自查）**：
- 这个任务里有没有**网络 I/O**？
- 有没有**调用本地脚本**（特别是 diting-skills 之外的脚本）？
- 有没有**多于 3 轮**的 LLM 推理？
- 有没有**等外部回应**（审批、第三方接口、用户手动操作）？

**任何一项答"是"就按"长"处理。**

---

## 二、长任务必须做的 4 件事

### 1. 分段执行 — 不要单次塞满

❌ 错：一个 ACP 会话里完成「拉 GitHub → 分析代码 → 写报告 → 推送到飞书」
✅ 对：拆成 4 个独立的 ACP 任务，每个任务交付一个中间产物：
1. 拉 GitHub → 输出 `repo-meta.json`
2. 分析代码 → 输出 `analysis.md`
3. 写报告 → 输出 `report.md`
4. 推送到飞书 → 单独执行

每个子任务**独立可重试**，失败一个不影响其他。

### 2. 设置任务超时上界（与 ACP 全局超时对齐）

OpenClaw 全局 ACP 超时见 `openclaw.json` → `acpx.config.timeoutSeconds`（事故修复后从 600s → 1800s）。

任务自身预算 = `min(ACP 全局超时 × 0.8, 业务期望上限)`。

例如：全局 1800s，业务期望 ≤ 20 min，则任务预算 = `min(1440, 1200) = 1200s`。

**在 prompt 里把预算告诉 Hermes**：
```
TIME_BUDGET: 1200s
  - 超过 80%（960s）时立即进入 Reflect，决定是否收尾
  - 超过 95%（1140s）时强制返回 status: "partial"，禁止再启动新动作
```

### 3. 进度回报 — 防止用户/系统判定挂死

每完成一个 ReAct 子步骤，立即回传一个轻量进度事件：
```json
{"event": "progress", "step": 3, "of": "≈ 8", "elapsed_s": 120, "last_action": "拉取 README"}
```

OpenClaw 收到进度事件后：
- 重置"无响应"计数器
- 可选：把进度同步给用户（"已读完 3/8 步，继续中..."）

### 4. Checkpoint — 失败后能从最近稳定点恢复

每完成一个独立可交付的中间产物（如 `repo-meta.json`），立即写入工作目录持久化文件。

```
workspace/
└── checkpoints/
    ├── 01-repo-meta.json        ← 第 1 段产物
    ├── 02-analysis.md           ← 第 2 段产物
    └── status.json              ← {"completed": [1, 2], "next": 3}
```

下次启动时先读 `status.json`，**只重跑未完成的段**。永远不要"从头再来"。

## 三、错误重试与死循环防护

事故中 thread binding 把用户消息反复路由到 error 会话，形成死循环。OpenClaw 在调度长任务时必须遵守：

### 1. 单任务硬上限：最多重试 N 次

```
RETRY_POLICY:
  max_attempts: 3
  backoff: [60s, 300s, 900s]   # 退避递增
  on_exhausted:
    - 解除 thread binding（如果是 persistent 会话）
    - 通知用户："这个任务跑了 3 次都超时，我先停下，给你两个选择..."
    - 写 incident 记录到 ~/.openclaw/incidents/ 供排查
```

### 2. 持续超时自动解绑

当同一个 ACP 会话**连续 ≥ 2 次超时**，必须：
1. 立即解除该会话与用户/线程的 binding
2. 把会话标记为 `quarantined`，新消息走新会话
3. 不要等用户继续发消息触发第 4 次超时

### 3. 失败后用户可见的表达

不要让用户感受到"还在转圈"，要让他知道**已经失败了，下一步怎么办**。

✅ 用：
> "这个任务我跑了 3 次都超时了，问题应该在拉 GitHub 那一步太慢。我先停下，两个选择：
> 1. 我换个更小的任务范围（只拉 README，不拉源码）
> 2. 你给我一个本地的代码副本，我直接读
> 你选哪个？"

❌ 不要用：
> "Background task timed out: acp-thread-xxx (run 7023)"

## 四、Persistent 会话的额外规则

`persistent` 模式下的 ACP 会话**会跨多次消息复用**，事故就是这种模式。额外规则：

| 规则 | 理由 |
|------|------|
| 每次复用 persistent 会话前，**先检查会话健康状态** | 避免向 error 状态会话继续投递任务 |
| `error` 状态超过 1 小时未恢复 → 自动废弃，建新会话 | 防止僵尸会话长期占用 binding |
| 新建 persistent 会话时，**记录预期最长生命周期** | 到期后主动清理，不留长尾 |
| persistent 会话不要承载"一次性"任务 | 一次性任务用 ephemeral 模式，跑完即释放 |

判定矩阵：

| 任务特性 | 推荐模式 |
|---------|---------|
| 单次执行、跑完即丢 | **ephemeral** |
| 需要保留对话历史的多轮交互 | persistent |
| 长时间后台分析、报告生成 | **拆成多个 ephemeral 子任务**，不要塞 persistent |

## 五、对 diting-skills 的兼容

diting-skills 的最小 demo 设计就是为了快速验证链路、避免长任务陷入。涉及长任务时遵守：

1. **diting-skills 的 doctor 和 min_demo 始终保持秒级**，永远不要把它们改成长任务
2. **真实业务的长任务不要混进 diting-skills 的 workspace**，避免 demo 验证被业务任务挂起干扰
3. 如果业务任务用到 diting-skills 的 prompt 模板（哨兵、STRICT MODE），**复制使用**，不要在 diting-skills 目录里跑业务任务

## 六、自查清单（每个长任务执行前过一遍）

```
[ACP 长任务自查]
- [ ] 估算了任务时长档（短/中/长/极长）
- [ ] 长任务已拆成多个独立子任务
- [ ] 每个子任务设置了 TIME_BUDGET（≤ 全局超时 × 80%）
- [ ] prompt 里要求 Hermes 输出进度事件
- [ ] 中间产物有 checkpoint 落盘
- [ ] 设置了 max_attempts 和退避策略
- [ ] persistent 会话使用前检查了健康状态
- [ ] 失败后有面向用户的自然语言话术
```

**任何一项答"否"，不要启动任务。** 先补齐再执行。

## 七、事故回顾

事故全文见 `issue-acp-thread-timeout-2026-04-23.md`。一句话教训：

> **"看起来只是一个稍微复杂点的任务"** 在 ACP persistent 模式下可能演变成死循环，单用户聊天彻底瘫痪。所有"稍微复杂"的任务都按长任务处理，加预算、加进度、加 checkpoint、加重试上限。
